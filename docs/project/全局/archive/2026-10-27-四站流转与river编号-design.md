所属模块：全局（跨 sea/ship/river/spring 四层；流动机制对 `全局/三层学习框架-design.md` Q4 的修订见第 10 节取代关系。注：文档成稿于 `学习/` 目录拆分前，落地时迁入本目录）

## 1. 背景与动机（开发者原话整理）

- 从实际应用场景来说，不需要 `/river add` 旧摘录功能，可以直接删除。
- 真实流转是：研读 sea 中的文件 → 直接在 sea 源文件基础上编辑（增删改内容，按自己需要二次加工）→ 自己判定加工完成后，把文件移入 river → 沉淀一段时间、非常熟悉之后，自己在 spring 手搓笔记文档。
- 补充：**加中间态 ship（船坞）**——开始加工但未完成时先放 ship；sea→ship、ship→river 都由开发者手动判定、手动触发。
- 延伸的重要问题：**笔记文件编号管理**——知识点多且杂，编号给用户自己看，方便整理与检索；怎样按 plan 多层树编号，增删时如何维护，需要设计。

## 2. 已确认的关键决策（brainstorming 问答记录）


| # | 问题                         | 决策                                                                                                                                                                                                          |
| --- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | 新流转与旧 `/river add` 关系 | **旧摘录语义整套删除**；新流程为「原文件加工后迁移」，不产生 river 新建条目                                                                                                                                   |
| 2 | 编号首要目的                 | 给用户自己看，方便整理与检索——文件名上能直接看出树序（编辑器/文件管理器里自然有序）                                                                                                                         |
| 3 | 编号覆盖层                   | **只 river/ship**；sea 保持原貌（杂多且多数不挂树），spring 沿用 `<知识点标题>.md` 约定不编号                                                                                                                 |
| 4 | 编号格式                     | **点位号 + 主干文件夹**：`Study/river/01-Go语言基础/03-slice底层结构与扩容.md`；同点多篇 `03.1-`、`03.2-`；主干号靠文件夹名表达，文件名不重复主干号（主干重排只改文件夹名，代价最小）；两位补零保证字符串排序 |
| 5 | 增删维护策略                 | **平时留空洞、显式重排**：新增领 max+1、删除留空洞；`/plan renumber` 显式全量重排 + 引用同步改写，由用户主动触发                                                                                              |

## 3. 四站流转模型

```
sea（大海）──/ship move──▶ ship（船坞·加工中）──/river move──▶ river（河流·沉淀）──手搓──▶ spring（泉水）
```

- **sea**：原貌保留；研读与二次加工直接在 sea 源文件上进行（外部编辑器编辑，gs 不介入内容）。
- **ship**：`Study/ship/` 平铺、不编号（中间态无需整理）；「开始加工」「加工完成」均由用户判定，手动触发命令流转。
- **river**：入河时领号改名、按主干归位；编号规则见第 5 节。
- **spring**：沿用现行 `/spring add <知识点>`（定位知识点 → 创建占位 → 自动绑定），本设计不动。

流转三动作全部是**用户显式命令**，无自动判定、无定时检测。

## 4. 数据模型增量（roadmap v2 保持 version=2，加可选字段）

```toml
[[branch.point]]
title = "select"
group = "基础原语"
status = "doing"
spring = "Study/spring/select.md"
river = ["Study/river/02-并发编程/02-select.md"]
ship  = ["Study/ship/select笔记.md"]   # 新增可选字段 0..N，缺省空
sea   = ["Study/sea/..."]
```

- `ship` 与 `sea`/`river` 同型：工作区相对路径数组，0..N；缺省视为空，旧 TOML 无需迁移。
- **绑定随文件流转**：`/ship move` 时路径从 `point.sea` 挪入 `point.ship`；`/river move` 时从 `point.ship` 挪入 `point.river`。文件不在任何 point 上时三数组均无记录，入河时追问挂载。
- planview 知识点详情页三段清单变四段：spring / river / **ship（加工中）** / sea。
- `/review` 三层统计追加「加工中 N 篇」（point.ship 引用计数 + ship 目录孤儿计数）。
- 约束沿 v2：绑定路径一律工作区相对路径；文件不存在标 `[失效]` 不自动清理；原子写；全局查重不变。

## 5. river 目录结构与编号规则

```
Study/river/
├── 01-Go语言基础/                    # <两位主干序>-<主干名>，序 = roadmap.toml branch 数组序
│   ├── 03-slice底层结构与扩容.md      # <点两位>-<标题>，序 = branch 内 point 数组序
│   └── 03.1-切片陷阱汇总.md           # 同点多篇：<点>.<篇序>-<标题>
├── 02-并发编程/
│   └── ...
└── 99-未挂载/                        # 入河时未挂 point 的收容区（不领号）
```

- 主干文件夹号与点位号都取自 **TOML 数组顺序**（TOML 是树序唯一权威）；两位补零保证编辑器字符串排序正确。
- 同点多篇篇序：首篇不带篇序（`<点两位>-<标题>.md`）；第 2 篇起 `.1`、`.2` 递增——入河领号取该 point 现有 river 文件的最大篇序 +1（仅有首篇时取 1）。
- 文件名标题默认沿用原名，剥掉常见源编号前缀（如 `1 `、`2.1 `、`1-3 `）；不合意可事后手编（gs 不拦）。
- spring 不编号（标题全局唯一已保证定位）；sea 不编号。
- `99-未挂载/` 内文件挂载 point 时（浏览器内后续挂载命令或手编 TOML + 重跑 renumber）归位领号。

## 6. 命令面


| 命令                   | 行为                                                                                                                                                                                                                                                                                                                       |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/ship move`            | 选择器挑 sea 文件（关键词过滤，沿现有选择器交互）→ 文件移入 `Study/ship/` → 绑定迁移 sea[]→ship[]（多归属点全部迁移）→ **自动打开编辑器**（装船即开工；沿 /spring add 命令末尾开编辑器的惯例）。旧 `/river add` 摘录流程（选择器挑 sea→编辑器删减→落 river→尾部追问挂载）整套删除，命令名不复用  |
| `/river move` | 选择器挑 ship 文件 → 已挂 point：领号改名入河 + 绑定 ship[]→river[]；未挂载：追问挂载（关键词过滤，可跳过 → 落 `99-未挂载/` 不领号）→ 完成后提示新旧路径                                                                                                                                                               |
| `/ship`                | ship 列表查看（复用现有 tier 查看 pager 模式）；`/sea` `/river` `/spring` `/ship` 四命令并列                                                                                                                                                                                                                               |
| `/plan renumber`       | **dry-run 先行**：预览全部改名/移动与引用改写清单，确认后执行。执行按 TOML 当前序全量归位：主干文件夹重命名、river 文件重命名（同点篇序紧凑化）、孤儿 river 文件（未挂 point）入 `99-未挂载/`、存量一次性归位；同步改写 roadmap.toml 绑定、topics.toml、全库出处链；执行前提示「工作区外引用（思源/Obsidian 等）不会同步」 |

`/plan` 其余子命令、`/sea` `/spring` 现有行为不变。

### 6.1 一次完整流转的操作示例（真实数据）

以 sea 文件 `Gin与Gee/5 中间件Middleware.md`、知识点「Web 工程化 › Gin 路由与中间件」（主干序 04、点序 01）为例：

```
# 第一段：装船（开始加工）
你：/ship move 中间件                  # 关键词可省略
gs：（选择器）sea 全部子文件夹中标题含「中间件」的文件 → ↑↓ Enter
gs：① Study/sea/Gin与Gee/5 中间件Middleware.md → Study/ship/5 中间件Middleware.md
    ② 绑定迁移：Web 工程化 › Gin 路由与中间件 的 sea[] → ship[]
    ③ 自动打开编辑器，开始加工
# 加工期间：编辑器随意改，gs 不介入；/plan 详情页该点 ship（加工中）段可见本篇

# 第二段：入河（宣告加工完成）
你：/river move
gs：（选择器）Study/ship/ 全部文件 → Enter
gs：① 反查绑定 → 挂在「Gin 路由与中间件」（04 主干 / 01 点）
    ② 领号：该点 river 已有首篇（01-Gin路由机制.md，无篇序）→ 本篇取篇序 .1
       Study/ship/5 中间件Middleware.md → Study/river/04-Web工程化/01.1-中间件Middleware.md
       （剥源编号前缀「5 」，标题沿原名；点位号 01 不变，同点多篇用 .N 区分）
    ③ 绑定迁移 ship[] → river[]
    ④ 全库出处链「> 出处：」行旧路径 → 新路径
    ⑤ 提示新旧路径
```

- ship 文件未挂任何 point 时，`/river move` 追问「挂到知识点？」（关键词过滤，回车跳过 → `99-未挂载/` 不领号）。
- 「加工完成」无任何自动判定：敲 `/river move` 即完成宣告；不敲则一直留在 ship。

## 7. 引用一致性与错误处理

**统一迁移管线**（sea→ship、ship→river、renumber 三类操作共用）：

1. 文件 `os.Rename`（同盘原子）；
2. roadmap.toml 绑定迁移（原子写）；
3. 全库出处链扫描改写（扫描 `Study/` 下所有 md 的 `> 出处：<路径>` 行，旧路径 → 新路径，逐文件原子写）。


| 场景                                     | 行为                                                                                                           |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| 步骤 2/3 中断                            | 提示「文件已移动、绑定/出处未同步」+ 涉及文件清单；绑定迁移可重入（幂等：按路径匹配），renumber 本身幂等可重跑 |
| 领号冲突（目标文件已存在）               | 篇序自动顺延重试；仍冲突则报错并列出冲突路径                                                                   |
| ship→river 时 point 不存在/关键词多匹配 | 沿现有选择器交互（多匹配弹 select）；跳过挂载入 99-未挂载                                                      |
| 出处链指向的 sea 文件被他人引用          | 全库改写覆盖所有引用方，不逐条确认（dry-run 阶段已列清单）                                                     |
| `Study/ship/` 不存在                     | 首次 `/ship move` 时自动创建                                                                                    |

## 8. 代码架构

```
internal/roadmap/          # 扩展（纯逻辑，不 import ui）
├── roadmap.go             # Point 加 Ship []string 字段；Load/Parse/Save 沿 v2
├── ops.go                 # BindShip/MoveBinding（sea[]→ship[]→river[] 幂等迁移）
└── renumber.go            # 新增：RenumberPlan 生成——(Roadmap, 文件树快照) → 改名清单 + 引用改写清单（纯函数，表驱动可测）

internal/tier/             # 新包：流转执行器（纯逻辑，可独立测试）
├── move.go                # MoveFile（rename + 目录创建）、领号（点位号/篇序计算）
└── chain.go               # 出处链扫描与批量改写（`> 出处：` 行识别替换，逐文件原子写）

internal/command/          # 装配层
├── tier_cmd.go            # /ship move、/river move；旧摘录流程删除
├── tier_view.go           # /ship 列表查看
├── plan.go                # /plan renumber 子命令装配（dry-run 渲染 + 确认执行）
└── review_stats.go        # 阶段 3：加工中统计追加于此

internal/planview/         # 阶段 3：详情页四段（spring/river/ship/sea）
```

- `roadmap`、`tier` 不 import ui；交互（选择器、确认、提示）全部留在 command 层。
- 领号与重排计划是纯函数：输入 TOML + 目录快照，输出确定性清单，单测不碰真实文件系统。

## 9. 分期与验收

- **阶段 1 · 主链路**：`ship` 字段 + `Study/ship/` + `/ship move` + `/river move` + `/ship` 列表；旧 `/river add` 摘录流程删除。
- **阶段 2 · 编号与重排**：`/plan renumber`（dry-run + 执行 + 引用改写）+ 存量归位（现 `river/02-Go核心/slice 底层结构与扩容.md` 为孤儿文件——roadmap 无任何 river 绑定，归位需先挂载 point，否则入 99-未挂载）。
- **阶段 3 · 视图增强**：planview 详情页四段 + `/review` 加工中统计。

每阶段验收：`go build ./...` + `go test ./...` 全绿；真机冒烟——sea 挑一篇 → `/ship move` → 编辑器加工 → `/river move` 入河领号 → `/plan` 浏览器绑定可见 → `/plan renumber` dry-run 预览与执行 → 出处链跳转（`o` 键）仍有效。

## 10. 取代关系

## 11. 范围外（本轮不做）

- sea 层编号与整理（保持原貌）。
- 自动判定加工状态、定时/启动时自动流转提醒。
- planview 浏览器内流转按键（r/m 等）——流转走命令层，浏览器保持只读+状态标记（与 plan浏览器重构 design 第 5 节「范围外」决策一致，后续可议）。
- `99-未挂载/` 文件的浏览器内挂载命令——v1 手编 TOML + 重跑 renumber 兜底，浏览器内挂载（a 键）待后续。
- ship→sea 回流（放弃加工）无专用命令——手动把文件移回 sea 原位 + 手编 TOML 清理 `ship[]` 绑定（未清理则树上标 `[失效]`，无害），v1 兜底。
